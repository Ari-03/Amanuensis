# Insertion and distribution plan

Checked September 19, 2026. This extends [macOS feasibility](macos-feasibility.md). Source inspection supports the approach below; Amanuensis has not yet passed these integration tests.

## Distribution decision

Recommend a directly distributed, Developer ID signed, notarized app with Hardened Runtime enabled and App Sandbox disabled. Cross-app dictation is the core workflow. Apple requires App Sandbox for App Store distribution and explicitly lists assistive accessibility API use among sandbox-incompatible activities. The starter project's enabled sandbox therefore needs an intentional change before the insertion spike. This recommendation does not imply that every possible dictation workflow is excluded from the store. A sandboxed recorder with manual copy would be a different product scope. [Apple sandbox requirements](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox)

VoiceInk provides a concrete production reference: its checked release entitlement file sets `com.apple.security.app-sandbox` to false. Do not copy its entitlement list wholesale; Amanuensis needs only capabilities its own integrations exercise. [VoiceInk entitlements, pinned revision](https://github.com/Beingpax/VoiceInk/blob/173cbb2b3aa0a18ab4035aa1bc9dc9fc215e88b6/VoiceInk/VoiceInk.entitlements)

## Evidence from real insertion code

VoiceInk snapshots readable data for every pasteboard item/type, writes transcript text with a unique paste-session marker, posts Command-V, and restores after a configurable delay only if it still owns that session. It checks accessibility trust before posting events. Its result deliberately reports `commandPosted`, not successful insertion. Current timing constants are 100 ms before paste, 10 ms between shortcut events, and a minimum 250 ms before restoration. These are implementation choices, not guarantees. [VoiceInk CursorPaster](https://github.com/Beingpax/VoiceInk/blob/173cbb2b3aa0a18ab4035aa1bc9dc9fc215e88b6/VoiceInk/Infrastructure/SystemIntegration/Paste/CursorPaster.swift)

Its clipboard helper adds transient/autogenerated markers and a session ID. Such markers are a compatibility courtesy to clipboard managers; they do not make clipboard data secret. Apple documents `changeCount` as an ownership-change counter, not acknowledgment that an editor consumed a paste. [Clipboard helper](https://github.com/Beingpax/VoiceInk/blob/173cbb2b3aa0a18ab4035aa1bc9dc9fc215e88b6/VoiceInk/Infrastructure/SystemIntegration/Paste/ClipboardManager.swift), [Apple changeCount](https://developer.apple.com/documentation/appkit/nspasteboard/changecount)

## Proposed Amanuensis behavior

Keep one serialized insertion service. Save the completed transcript before attempting insertion. Capture the destination process and focused accessibility element when recording starts; keep the recording panel nonactivating. Immediately before paste, compare the current destination with the captured one. If the app, window, or identifiable field changed, retain the result and offer Copy or an explicit insertion action. Do not reactivate an old app automatically or insert into whatever happens to be frontmost after a long transcription.

Accessibility cannot describe every custom editor reliably. Unknown focus requires a visible, recoverable fallback. Recognized secure text fields should not receive automatic dictation. This is a product safeguard, not proof that all secure fields can be identified.

Snapshot all readable clipboard representations immediately before replacement. Record both the resulting ownership counter and our session marker. Restore only if both still match. Skip restoration when the user copies something else, including text identical to the transcript. Unreadable promised data, a crashed app, and slow asynchronous paste targets remain limitations. Expose preservation behavior honestly and keep manual Copy available. Never retry paste automatically when success is uncertain, because duplicate insertion is worse than a copyable result.

Start with clipboard plus synthetic paste. Evaluate accessibility insertion separately for specific editors; do not replace an entire field's value as a generic fallback. Leave auto-send disabled and outside the first insertion spike.

## Permissions and shortcut choice

Use KeyboardShortcuts for configurable ordinary key combinations, including key-down/key-up for push-to-talk. It documents no permission dialogs and supplies a SwiftUI recorder. Fn and modifier-only shortcuts need a separate event-tap implementation. [KeyboardShortcuts](https://github.com/sindresorhus/KeyboardShortcuts)

Ask for microphone access when recording is first used and accessibility when automatic insertion is enabled. `AXIsProcessTrustedWithOptions` reports current trust; its prompt is asynchronous. Check event-listening access separately when enabling special shortcuts. Do not claim all users need Input Monitoring for ordinary shortcut registration. [Apple accessibility trust](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions), [event-listening preflight](https://developer.apple.com/documentation/coregraphics/cgpreflightlisteneventaccess())

VoiceInk's event tap tracks modifiers, suppresses matched events, resets held shortcuts after tap interruption, and handles disabled taps. Treat these as necessary scenarios to test for Fn/PTT. No keyboard event contents should enter logs. [VoiceInk shortcut monitor](https://github.com/Beingpax/VoiceInk/blob/173cbb2b3aa0a18ab4035aa1bc9dc9fc215e88b6/VoiceInk/Features/Shortcuts/Coordination/ShortcutMonitor.swift)

## Narrow spikes before broad UI

1. Build a signed helper-sized app with a nonactivating panel, one editable shortcut, canned text, and permission status. Run outside Xcode from a stable install path. Test grant, denial, revocation, restart, and a second signed build. Passing means permission behavior is understood under the intended distribution configuration.
2. Paste short, multiline, and large transcripts into TextEdit, Mail, Messages, Safari/Chrome editors, VS Code, and T3 Code where installed. Test selections, rich clipboard content, user copying during paste, keyboard layouts, and held modifiers. Record observed insertion separately from event-post success. Any wrong-destination paste fails the spike.
3. Change app/window/field during a delayed result; open the mode picker; cancel, lock, sleep, and disconnect a keyboard during PTT. Verify recovery without unwanted insertion or a stuck microphone. Test Fn against system Globe shortcuts on actual hardware.
4. Repeat the successful flow in a notarized release build on a clean user account. Until then, report development validation only. Model inference and broad screen construction can proceed independently, but should not obscure an unresolved insertion failure.

## Release and updates

Archive and sign all executables and embedded frameworks with Developer ID, enable Hardened Runtime, include secure timestamps, notarize, and staple the ticket. Keep release entitlements minimal and exclude `get-task-allow`. Test the downloaded artifact through Gatekeeper. [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

Use Sparkle 2 with an HTTPS appcast and Ed25519-signed update archives. Keep update keys outside the hosting environment. Test an actual older-to-newer signed update, including permission continuity and retained models/history. Add a Check for Updates control only when a working feed exists. No certificates, accounts, feeds, or provisioning were changed during this research. [Sparkle setup and release testing](https://sparkle-project.org/documentation/)
